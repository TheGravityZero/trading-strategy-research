# Liquidation Cascades: Task List

Цель проекта: исследовать и реализовать стратегию, которая определяет фазы
ликвидационного каскада на криптовалютных perpetual futures:

1. начало импульса;
2. forced continuation;
3. exhaustion и возможный reversal.

Главный результат — воспроизводимый event-driven backtest с реалистичными
комиссиями и проскальзыванием, а не просто высокая точность ML-модели.

## Milestone 0 — Спецификация эксперимента

- [ ] Выбрать биржу для MVP: Binance USD-M Futures.
- [ ] Выбрать universe: BTC, ETH и 20–30 наиболее ликвидных perpetual futures.
- [ ] Зафиксировать период исследования и untouched test period.
- [ ] Выбрать базовую частоту данных: 1 минута.
- [ ] Зафиксировать горизонты:
  - continuation: 1–5 минут;
  - reversal: 5–30 минут.
- [ ] Определить торговые ограничения:
  - максимальный leverage;
  - размер позиции;
  - лимит позиции относительно минутного объёма;
  - максимальное время удержания.
- [ ] Записать исходную гипотезу и условия её опровержения.

**Готово, когда:** существует короткий experiment spec, параметры которого не
меняются после просмотра test period.

## Milestone 2 — Исследование событий

- [ ] Рассчитать rolling-признаки без использования будущих данных:
  - returns на 1/3/5/15 минутах;
  - realized volatility;
  - volume z-score;
  - taker imbalance;
  - изменение open interest;
  - отклонение от VWAP;
  - funding percentile.
- [ ] Нормализовать признаки отдельно по активам и времени суток.
- [ ] Реализовать причинный детектор каскада:
  - экстремальное движение цены;
  - аномальный объём;
  - падение OI;
  - рост realized volatility.
- [ ] Не допускать повторного создания одного события на каждой минуте каскада.
- [ ] Объединять синхронные события альткоинов в один market-wide cluster.
- [ ] Разделить long-liquidation и short-liquidation cascades.
- [ ] Построить event-study графики:
  - cumulative return до и после события;
  - OI;
  - volume;
  - taker imbalance;
  - volatility;
  - spread, если доступен.
- [ ] Сравнить события по активам, годам и рыночным режимам.
- [ ] Оценить число независимых событий.

**Готово, когда:** детектор находит визуально и статистически осмысленные
события, а результаты не основаны на нескольких выбросах.

## Milestone 3 — Baseline-стратегии

### Continuation baseline

- [ ] Входить по направлению импульса после срабатывания детектора.
- [ ] Реализовать time exit.
- [ ] Добавить stop-loss и take-profit.
- [ ] Перебрать небольшой заранее заданный набор горизонтов.

### Reversal baseline

- [ ] Определить exhaustion через замедление цены.
- [ ] Рассчитать proxy price impact:

  `abs(price change) / (abnormal volume + epsilon)`

- [ ] Проверить гипотезу: высокий объём при падающем impact предшествует reversal.
- [ ] Добавить подтверждение через восстановление taker imbalance.
- [ ] Реализовать вход против исходного движения.

### Общие проверки

- [ ] Сравнить результаты с random-entry и простым contrarian baseline.
- [ ] Оценить gross PnL до комиссий.
- [ ] Добавить taker fees и funding.
- [ ] Провести sensitivity analysis параметров.

**Готово, когда:** понятно, существует ли эффект до ML и переживает ли он
базовые торговые издержки.

## Milestone 4 — Разметка

- [ ] Определить causal anchor — момент, когда стратегия реально может войти.
- [ ] Реализовать triple-barrier labeling:
  - take-profit;
  - stop-loss;
  - time barrier.
- [ ] Создать отдельные targets:
  - продолжение движения;
  - reversal;
  - максимальное благоприятное движение;
  - максимальное неблагоприятное движение.
- [ ] Исключить признаки, рассчитанные после anchor.
- [ ] Проверить overlap между train/validation/test событиями.
- [ ] Реализовать purge и embargo для пересекающихся горизонтов.
- [ ] Проверить баланс классов и устойчивость label definition.

**Готово, когда:** для каждой строки можно объяснить момент принятия решения,
доступные тогда данные и способ получения label.

## Milestone 5 — ML-модели

### Baselines

- [ ] Logistic regression.
- [ ] Неглубокое decision tree для интерпретации.
- [ ] Gradient boosting.

### Основная модель

- [ ] Реализовать небольшой temporal MLP или TCN в PyTorch.
- [ ] Добавить признаки состояния рынка BTC/ETH.
- [ ] Добавить embedding актива только после проверки out-of-sample переноса.
- [ ] При необходимости реализовать multi-task модель:
  - вероятность continuation;
  - вероятность reversal;
  - expected return.

### Валидация

- [ ] Использовать walk-forward validation.
- [ ] Подбирать параметры только внутри train/validation.
- [ ] Калибровать вероятности.
- [ ] Считать:
  - ROC-AUC и PR-AUC;
  - Brier score;
  - precision в верхнем квантиле;
  - expected return по квантилям прогноза;
  - PnL после costs.
- [ ] Провести feature ablation.
- [ ] Проверить стабильность feature importance.

**Готово, когда:** ML статистически и экономически превосходит rule-based
baseline на нескольких walk-forward окнах.

## Go / No-Go критерии

Продолжать разработку стратегии, если:

- [ ] эффект наблюдается на нескольких временных периодах;
- [ ] результат не определяется одним активом или несколькими событиями;
- [ ] доходность монотонна по силе сигнала;
- [ ] baseline остаётся положительным после разумных costs;
- [ ] результат выдерживает увеличение costs и latency;
- [ ] untouched test подтверждает хотя бы направление эффекта.

Остановить или пересмотреть гипотезу, если:

- [ ] эффект возникает только при выборе параметров на test;
- [ ] PnL исчезает после реалистичного spread/slippage;
- [ ] стратегия зависит от недоступной в реальном времени информации;
- [ ] независимых событий недостаточно для вывода;
- [ ] результат объясняется обычной экспозицией к BTC;
- [ ] ML улучшает offline-метрику, но ухудшает net PnL.
